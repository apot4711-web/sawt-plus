## Session 13 (2026-10-21) — P0 crash/lifecycle fixes

Read `AGENTS.md`/`STATE.md` first; the read-only inspection was delegated to the
`explore` subagent, as requested. No downloads, installs, or commits were made.
The live daemon (PID 352740, `127.0.0.1:8787`) was not touched.

Fixed (working tree only):

- **P0-1 subscriber race.** `broadcast`/`broadcastPCM` now hold `d.mu.RLock`
  for the non-blocking sends, and `Subscribe`/`Feed` cancel funcs only
  unregister; they never close a channel. `Shutdown` deletes then closes the
  remaining channels under the write lock after all producers have stopped.
  `Subscribe`/`Feed` after shutdown return an already-closed channel.
  While testing this, `Status()` was found to take a nested `d.mu.RLock` via
  `sourceDropped()`; a pending writer made that deadlock. `Status()` now
  snapshots `d.source` under the lock and calls `Stats()` outside it.
- **P0-2 WaitGroup misuse.** `StartStream` checks `closed` and does `wg.Add(1)`
  under `d.mu` (the same lock `Shutdown` uses to set `closed`), so `Add` can
  never race with `Wait`. A `streamMu` serializes concurrent starts, and
  starting after `Shutdown` returns the new `ErrClosed`.
- **P0-4 name/ID targets.** `ResolveDevice` keeps the saved `Address` when the
  target is a name or ID and only normalizes/replaces it for network targets
  (contains `:`). `Unpair` also removes by `Name`. Tests cover resolve by
  name/ID/address and unpair by name.
- **P0-5 single instance.** `config.AcquireDaemonLock` uses `flock` on
  `~/.config/sawt-plus/daemon.lock` (PID written for diagnostics); `runDaemon`
  holds it for its lifetime, so a second daemon exits with
  "another sawt daemon is already running". `UpdateConfig` now rejects
  `web_addr` changes while running instead of silently diverging from the
  listener.
- **P0-6 stale IP.** After 3 consecutive failed Wi-Fi dials, `wifiLoop` runs
  discovery for 3 s, matches the saved device by stable `ID` (name fallback),
  updates the saved address/token entry, logs it, and retries immediately.
- **P1-7 config durability.** `Config.Save` writes a `0600` temp file, fsyncs,
  and renames it over `config.toml`. `LoadAPIToken` tightens an existing token
  file to `0600` and regenerates a short/corrupt file after retries.
- **P1-8 gain 0.** `normalize()` only defaults a negative gain, so `0` persists.

### P0 — correctness / security (do these first)

1. **Daemon can panic on subscriber close.** `Daemon.broadcast`,
   `broadcastPCM`, `Subscribe`, and `Feed` copy the subscriber list and send
   after releasing `d.mu`; a concurrent unsubscribe (`cancel()`) or `Shutdown`
   closes the channel in between, so the send hits a closed channel
   (`send on closed channel` panic). This can be triggered by closing a browser
   tab while audio is flowing (status is broadcast ~50×/s).
   - `internal/daemon/daemon.go:233` (`broadcast`)
   - `internal/daemon/daemon.go:248` (`Subscribe`/cancel closes channel)
   - `internal/daemon/daemon.go:279` (`broadcastPCM`)
   - `internal/daemon/daemon.go:1008` (`Shutdown` closes channels)
   - Fix direction: never close subscriber channels from `cancel`; add a
     per-subscriber `done`/closed flag and unregister under the same lock used
     for the send, or send with `d.mu.RLock` held (sends are non-blocking) and
     close only after `Shutdown` has stopped all producers. Add a regression
     test that subscribes, broadcasts, unsubscribes, and broadcasts again
     under `-race`.

2. **WaitGroup misuse risk on shutdown.** `StartStream`/`StartStream("adb")`
   call `d.wg.Add(1)` while `Shutdown` may already be in `d.wg.Wait()`;
   an in-flight API request during shutdown can panic with
   "WaitGroup is reused before previous Wait has returned".
   - `internal/daemon/daemon.go:476`, `:497`, `:1005`
   - Fix direction: add a `closed`/lifecycle guard around `Add`, or use a
     dedicated per-stream goroutine set joined before shutdown.

3. **No TLS, and tokens are permanent.** Audio and the pairing token travel as
   plaintext `ws://` on the LAN. Anyone who sniffs a token once can listen to
   the microphone forever. There is no phone-side revocation list, no token
   expiry, no per-device naming, and limits are missing.
   - `internal/daemon/daemon.go:559` (dial), `:834` (pair dial)
   - `WifiServer.java:129-146` (tokens are only ever added)
   - `WifiServer.java:515` (mDNS advertises `pair=1` permanently)
   - Fix direction: TLS (`wss://`) with a paired certificate/fingerprint, or at
     minimum encrypt the token channel; add "forget all PCs"/revoke on the
     phone and cap stored tokens.

4. **Connecting/unpairing by device name or ID is broken.**
   `ResolveDevice` finds a saved entry by name/ID, then overwrites
   `entry.Address` with `NormalizeAddress(target)`. For a name this yields
   e.g. `Sawt+:8765`, so `sawt connect NAME` (advertised in help) and
   `sawt unpair NAME` fail or leave the stream running.
   - `internal/daemon/daemon.go:448-459`
   - `cmd/sawt/main.go:798` (help promises `name` is a valid target)
   - Fix direction: only overwrite the address when the target looks like a
     network address (contains `:`) or no saved entry was found; keep the
     saved `entry.Address`/`entry.ID` otherwise. Add unit tests for
     connect-by-name, connect-by-ID, unpair-by-name.

5. **Multiple daemons can run at once and fight over PipeWire.**
   There is no lock/PID file. `web_addr` can be changed through
   `PUT /api/config` but the running listener does not rebind, so the CLI
   cannot reach the daemon at the new address and starts a second daemon.
   Both then call `unloadExisting`, unloading each other's
   `module-pipe-source` and writing to the same FIFO.
   - `internal/daemon/daemon.go:1047-1059` (`UpdateConfig` accepts `web_addr`)
   - `internal/audio/pipe.go:194-211` (`unloadExisting`)
   - `cmd/sawt/main.go:160-187` (hybrid autostart has no lock)
   - Fix direction: a `flock`/PID lock in the config dir, reject or restart on
     `web_addr` changes, and make `Source.Start` fail fast if another live
     daemon owns the source.

6. **Reconnect uses a stale saved IP.** `StartAutoConnect` and `wifiLoop`
   retry the stored address forever; if the phone's DHCP lease changes, the PC
   never re-discovers it and the user must re-pair.
   - `internal/daemon/daemon.go:978-992`, `:521-553`
   - Fix direction: after N failed dials, run mDNS/avahi discovery, match by
     device ID, update the saved address (and log it), then retry.

### P1 — reliability / data integrity / UX

7. **Config is written non-atomically and permissions are not enforced.**
   `Config.Save` truncates `config.toml` in place; a crash/power loss can
   corrupt it and lose all pairing tokens. `os.WriteFile` does not change the
   mode of an existing file, and `LoadAPIToken` does not verify the mode of an
   existing token file (a legacy 0644 file stays readable by other local
   users). A short/corrupt token file makes `LoadAPIToken` sleep and fail
   instead of regenerating it.
   - `internal/config/config.go:212-221`, `:100-147`
   - Fix direction: temp file + `fsync` + `rename`; `chmod 0600` on load/save;
     regenerate an invalid token file (with an explicit warning).

8. **`gain = 0` cannot be persisted.** `SetGain(0)` is allowed and saved, but
   `normalize()` treats `Gain <= 0` as "unset" and resets it to 1.0 on the next
   load.
   - `internal/config/config.go:192-194`
   - Fix direction: only default a missing/unset gain (e.g. `< 0`, or a
     separate `set` flag), and keep 0 valid.

9. **Status is broadcast 50×/s.** `ProcessPCM` calls `broadcastStatus()` for
   every 20 ms frame, i.e. one full status JSON per frame to every SSE client,
   plus a `sourceDropped()` stats call. Wasteful CPU/battery and UI churn.
   - `internal/daemon/daemon.go:742-770`
   - Fix direction: throttle status events (~5-10/s) and broadcast
     counters/frames separately from the status snapshot.

10. **Latency can grow to ~1 s under congestion.** The phone's per-client queue
    is 48 frames (~960 ms), the PipeWire source queue is 48 frames, and the
    browser feed queue is 16; there is no latency budget, no metrics, and no
    adaptive drop policy beyond "drop oldest". QoS is not measured anywhere.
    - `WifiServer.java:673` (`ArrayBlockingQueue<>(48)`)
    - `internal/audio/pipe.go:52`, `:158-163`
    - `internal/daemon/daemon.go:263-294`
    - Fix direction: smaller queues + measured end-to-end latency in
      `Status`, and a documented target (e.g. <150 ms LAN).

11. **No sample-rate fallback.** `AudioCapture` gives up if 48 kHz is not
    supported; no 44.1 kHz attempt and no resampling on the PC.
    - `AudioCapture.java:46-51`
    - Related open risk already noted: some ROMs may refuse 48 kHz.

12. **Android lifecycle/threading rough edges.** `AudioRecord.read` may return
    a partial frame (no accumulator / odd-length guard), `stop()` can block
    the main thread up to 1 s, `WifiServer.stop(1000)` runs on the main thread,
    and the `MAX_CLIENTS` check is not atomic with `clients.put`.
    - `AudioCapture.java:88-129`
    - `WifiServer.java:265-273`
    - `RecordService.java:93-98`, `:148-157`

13. **Phone WebSocket has no origin check and is open on all interfaces.**
    Any local web page can open a WebSocket to the phone and try pairing. The
    per-IP throttle (single-use code, 30 s cap) makes brute force impractical,
    but the exposure is avoidable. Also consider binding only to the Wi-Fi
    interface.
    - `WifiServer.java:146-162`, `:632-644`

14. **Discovery false positives / gaps.** mDNS TXT always advertises `pair=1`,
    so `sawt discover` shows "required" even for a paired PC. The active scan
    probes only `8765`, while the app can bind `8765..8774`; and any unrelated
    WebSocket server on 8765 is reported as a Sawt device because only the
    `101` upgrade is checked.
    - `WifiServer.java:515`
    - `internal/discovery/discovery.go:317-373`
    - Fix direction: advertise the real paired state; scan the port range;
      validate identity (mDNS TXT `id` or a `hello`/`pair_required` probe).

## Goal

Turn the original USB/ADB-only `gdzx/audiosource` into `Audio Source+`:
a wireless microphone that streams Android mic audio to a Linux machine over
Wi-Fi, controlled from the terminal, with an on-demand browser UI. ADB remains
as a fallback. No TUI.

## Approved decisions

- New project, new app id; do not modify the original project or F-Droid app.
- Go for the CLI/daemon. No TUI as the product interface.
- Primary UX: terminal commands. Optional GUI: plain HTML/CSS/JS embedded in
  the Go binary and served by the daemon, Syncthing-style (headless daemon,
  UI only when opened). No npm/Svelte build step.
- Native Wi-Fi streaming first, ADB fallback second.
- Protocol: WebSocket text control + binary PCM frames, `s16le`, 48000 Hz,
  mono, 20 ms per frame.
- Control messages: `hello`, `pair`, `pair_required`, `paired`, `ready`,
  `ping`, `pong`, `stats`, `error`.
- Token stored as SHA-256 on the phone. 6-digit pairing code valid 10 minutes.
- mDNS service `_sawtplus._tcp.` with TXT `id`, `name`, `v`, `pair`.
- Local network `ws://` for now; TLS is a later phase.
